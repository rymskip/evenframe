# feat(validators): excludes

- **Date:** 2026-11-03 22:55
- **Commit:** 11a80ed
- **Area:** Validators, typesync, schemasync

## Problem

A value that must not hold some text, such as a path segment refusing `/`, `\` and control characters, could only say so through a `regex_literal`. The portable regex subset has no lookahead, so the pattern had to be written as everything the value may hold, which reads badly and is easy to get wrong.

## Fix

`excludes = "text"` and `excludes = format(...)` refuse a value holding the text, or any match of the format, anywhere in it. A custom format may not carry its own `^` or `$`, as in the other positional checks.

- Rust: the negation of `includes`, reported as `must be a value without ...`.
- ArkType and Effect: a negated predicate; Macroforge: an `excludesText` helper, since its `includes` has no negation.
- SurrealDB: `!(...)` around the `includes` assertion.
- Protobuf: one plain-text exclusion as `not_contains`. A further one, or an excluded format, is listed as a check the output cannot express.
- FlatBuffers: `excludes("...")` for text and `notPattern("...")` for a format.

## Verified

- Derive test `excludes_refuses_a_value_holding_its_text_or_format`, SurrealQL assertion tests, and the parser's anchor check.
- The new `excludes` spec, snapshotted for every generator.
- `generated_check` runtime cases: ArkType and Effect accept a clean segment and refuse a slash, a backslash, a control character, a delete character and an excluded digit.
- `pixi run verify`: every step passed, protoc and flatc compiling the new schemas.
