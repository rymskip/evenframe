# chore(deps): move to SurrealDB 4.0.1 and Rust 1.100.0 as 0.7.0

- **Date:** 2026-11-22 22:55
- **Commit:** this commit
- **Area:** Dependencies, schemasync, the CLI runtime, tests, docs

## Problem

A SurrealDB 3 client refuses a 4.0 server, so schemasync could not connect to one. Once
connected, SurrealDB 4.0 refused or mishandled parts of the schema evenframe generates:

- A `DEFAULT` on a field typed as another table's record did not coerce to `record<table>`, so
  the `DEFINE FIELD` failed.
- The JavaScript `ASSERT`s some validators emitted were refused: a schema clause may not run a
  script.
- A validator nested in an array, map or enum payload was asserted with `array::all` and a
  closure. A field or event clause that makes a closure cannot run under a definition's
  `AUTH LIMIT`, so every write to such a table failed with "IR entry point not implemented".
- After an analyzer changed, re-applying its dependent full-text index with the same
  definition did not reindex it, so a search kept answering from the old analyzer's tokens.
- The in-memory engine overflowed tokio's 2 MiB worker stack, and the test threads' 2 MiB
  stack, on a deep error path.

The stored names under `#[surreal(rename_all)]` now match the SDK's derive exactly, so the test
pinning their old difference failed.

## Cause

SurrealDB 4.0 changed the rules the generator relied on: field clauses must coerce and may not
script or make closures, an identical index overwrite is a no-op, and the SDK's derive moved to
heck 0.5, the version evenframe already used.

## Introduced

Outside this repository: SurrealDB 4.0. The generated `DEFAULT`, the JavaScript and closure
asserts and the index overwrite were correct against SurrealDB 3.

## Fix

- `surrealdb` and `surrealdb-types` 4.0.1, the stable 1.100.0 toolchain, every crate at its
  newest release (`cargo upgrade --incompatible`, then `cargo update` in both workspaces), and
  the crates at 0.7.0. The docs pin `0.7`.
- A field typed as another table's record takes no generated `DEFAULT`.
- Asserts are native only: the JavaScript forms and `scripting_asserts` are gone. A validator
  with no SurrealQL form (a checksum, JSON or regex parsing, Unicode normal forms) asserts
  nothing in the schema; Rust and TypeScript still check it.
- A nested validator is asserted with a `[WHERE …]` filter: `array::len(xs[WHERE !(P)]) = 0`,
  each value named `$this`.
- Schemasync rebuilds each modified index (`REBUILD INDEX`) after redefining it.
- The CLI runs on a runtime with 10 MiB worker stacks, and the repo's test threads get 10 MiB
  (`RUST_MIN_STACK`), as SurrealDB documents for an embedded engine.
- `SurqlOptions` keeps only `option_none`, and `tables_surql` takes it directly.
- The casing test pins that the stored names match the SDK in every casing.
- The insta and similar `opt-level` overrides are gone: trybuild copies the profile into its
  test project, which has neither, and warned about both.

## Verified

Against the finished branch: `pixi run verify` passed all 12 steps (run `20261123T035543Z`,
1704 tests), and `verify --pipeline derive-check,tests` passed with no warning after the profile
overrides went (run `20261123T045118Z`). The testground database e2e passed 29 of 29 against
SurrealDB 4.0.1. Against the 4.0.1 server in memory: the filter asserts stored a valid record and
refused each invalid one, a closure in an event body made the write fail while one in a
function did not, and a `REBUILD INDEX` after an analyzer change made a stemmed term match where
the identical `DEFINE INDEX OVERWRITE` did not.
